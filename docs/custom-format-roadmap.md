# 専用フォーマット構想（ロードマップ）

> ステータス: 構想段階（未実装）。実装前の合意形成用ドキュメント。

## 0. 確定要件（MUST）

> チャット形式のLLM（Gemini / ChatGPT / Claude）に対し、**1ファイル**でディレクトリの中身を厳密に読み込ませ、作業後は編集後の状態を**厳密にディレクトリとして再現できる**こと。

- 対象は特定のAIサービスに限定しない。Gemini・ChatGPT・Claude、いずれのチャットUIに貼り付けても同じ精度で読み書きできることが必須。
- 「厳密に」とは、ファイル境界・パス・内容（改行やインデントを含む）が一切のブレなく round-trip できることを指す。曖昧な自然言語的解釈に依存しない。
- この要件により、フォーマットは特定プラットフォーム専用機能（Gemini Gemのシステム指示や、特定のコード実行ツール）に依存しすぎない設計が必須となる（§3・§5参照）。
- **判断基準は「人間が読めるかどうか」ではなく「LLMが齟齬なく扱えるかどうか」**。人間可読性は採否の決定要因にしない（§3参照）。

## 1. 背景・課題

現状の EasyToVibe は、プロジェクトのディレクトリ構造とソースコードを **1つの Markdown ファイル**に集約し、Gemini などのAIエージェントに貼り付けて読ませる、という一方向のワークフローのみをサポートしている（[extension.js](../extension.js)）。

この Markdown 方式には、精度・再現性の面で以下の限界がある。

- **コードフェンス衝突**: ソースコード中に ` ``` ` が含まれる場合、Markdown の出力側コードフェンスと衝突し、構造が壊れる。
- **バイナリ非対応**: 画像・フォントなどのバイナリファイルは表現できない。
- **パスの曖昧性**: ツリー表記とファイル本文の対応関係が厳密な文法で定義されておらず、AI側の解釈にブレが生じうる。
- **一方向のみ**: 「エクスポート → AIに読ませる → コピペで手動反映」までしかできず、AIが編集した結果を機械的に元のディレクトリ構造へ戻す手段がない。

## 2. やりたいこと（将来フロー）

```
[プロジェクト] --(拡張機能: export)--> [専用フォーマットファイル（1ファイル）]
                                            |
                                            v
                    チャットLLM（Gemini / ChatGPT / Claude いずれか）が編集作業
                                            |
                                            v
[専用フォーマットファイル] --(拡張機能: import)--> [プロジェクト（通常のディレクトリ構造）]
```

1. 拡張機能がプロジェクトを **専用拡張子の1ファイル**としてエクスポートする（ディレクトリ構造 + ファイル内容を厳密な文法で表現）。
2. そのファイルを、Gemini・ChatGPT・Claude いずれかのチャットに読み込ませて作業してもらう。
3. LLM は完成品を **同じ専用フォーマット**で出力する。
4. 拡張機能がそのファイルを読み込み、通常のディレクトリ／ファイル構造に厳密に復元する。
5. どのLLMでも読み書き精度を担保できるよう、文法自体をプラットフォーム非依存でシンプル・厳密にし、必要に応じて各プラットフォームのカスタム指示機能（Gemini Gem／ChatGPT Custom GPT／Claude Projectのカスタム指示）で文法を教え込む（§5参照）。

## 3. フォーマット方式の検討

判断基準は一貫して **「LLMが齟齬なく読み書きできるか」** のみ。人間可読性は採否には影響しない（可読でなくても、LLMが完全に無矛盾に扱えるなら採用候補になり得る）。

| 方式 | メリット | 懸念点（要検証） |
|---|---|---|
| **テキストベース独自プロトコル**（第一候補・実装から着手） | Gemini・ChatGPT・Claude いずれのチャットにも直接貼り付け可能（アップロード機能やコード実行ツールに依存しない）。既存の Markdown 出力からの延長で実装しやすい。 | 後述（§4）の通り、LLM が出力時に `bytes=` のような長さ情報を寸分違わず計算できるかは未検証。 |
| **zip 等バイナリ圧縮**（採用検討の対象。要検証） | ファイルサイズを削減できる。バイナリファイルもそのまま格納可能。 | チャットUIへの貼り付けができないため、アップロード＋コード実行ツール（unzip/zip）経由が前提になる。3プラットフォームともコード実行機能自体は存在するが、①ツールが必ず起動される保証、②生成物が壊れず（byte-exactに）ダウンロードできる保証、を実際に検証していない。ここが確認できれば採用候補として復帰する。 |

→ 現時点では **実装の着手しやすさ・チャット直接貼り付けの手軽さ**からテキストベースを第一候補として先に実装するが、これは「zipはLLMに理解できないから却下」という意味ではない。zipは **「3プラットフォームでコード実行ツール経由でも齟齬なく扱えるか」を検証した上で** 採用候補に含める（§6 未決事項に検証タスクを追加）。

## 4. テキストベースフォーマットの文法案（たたき台）

コードフェンス衝突を避けるため、ファイル内容の開始・終了を **一意なマーカー行 + 内容のバイト長** で区切る案。

```
#ETV-FORMAT v1
#ROOT <project-name>

#TREE-BEGIN
<project-name>/
├── src/
│   └── index.js
└── package.json
#TREE-END

#FILE-BEGIN path="src/index.js" bytes=123 encoding="utf-8"
<...ファイル内容（bytes分だけ厳密に読む。内容中のマーカー文字列と衝突しない）...>
#FILE-END

#FILE-BEGIN path="package.json" bytes=45 encoding="utf-8"
<...>
#FILE-END
```

ポイント:
- `#FILE-BEGIN` / `#FILE-END` は目印であると同時に、`bytes=` の値で本文を厳密に切り出せるため、内容中に同じ文字列が現れても衝突しない。
- `path` は常にプロジェクトルートからの相対パスで統一し、区切り文字は `/` に固定（Windows/Mac/Linux差異を吸収）。
- 将来のバイナリ対応として `encoding="base64"` を選べるようにしておく。
- 拡張子は例として `.etv`（EasyToVibe）を仮称とする。

**懸念点（要検証）**: `bytes=` はプログラム（拡張機能側のパーサー）が正確に扱う分には問題ないが、LLM自身が編集後の出力でこの値を寸分違わず計算できるかは別問題。特に日本語などマルチバイトUTF-8を含む内容では、LLMが「文字数」と「バイト数」を混同したり計算を誤ったりするリスクがある（LLMは正確なカウント処理が苦手）。これはbase64（バイナリ対応）でも同様に「LLMが変換を一切誤らずに扱えるか」が問われる、§3の懸念点と本質的に同じ問題。
→ 対策候補: ①`bytes=`をLLMに計算させず一意なランダム文字列マーカー（衝突がほぼ起こり得ない）だけで区切り、長さ情報は省略する。②拡張機能のimport側で`bytes=`の値を信用せずマーカー文字列の再検出で境界を決め、`bytes=`は補助的な検証用にとどめる。③実際に3プラットフォームでLLMに編集させて、境界がズレないかを実地検証する。
→ この検証を経てから文法を正式確定する（§6）。

※ この文法は初期たたき台であり、実装前に確定させる必要がある（次の設計フェーズで詰める）。

## 5. プラットフォーム側カスタム指示の役割

§0 のMUST要件（3プラットフォーム共通での厳密round-trip）を満たすため、以下の二段構えで精度を担保する。

1. **文法自体をシンプル・厳密にする（本質的な担保）**: §4 の文法はマーカー行 + `bytes=` によるバイト長指定で、自由記述の余地がないよう設計する。カスタム指示なしの素のプロンプト＋この文法説明だけでも、どのLLMでも読み書きできることを目指す。
2. **各プラットフォームのカスタム指示機能（補助的な担保）**: 精度をさらに高めるため、対応する場合は各プラットフォームの仕組みを使って文法を教え込む。
   - Gemini: Gem のシステム指示
   - ChatGPT: Custom GPT の Instructions
   - Claude: Project のカスタム指示 / CLAUDE.md 相当
   - これらの指示文言は同一の内容（§4の文法説明）をベースにし、このリポジトリ内でバージョン管理する（将来的に `docs/prompts/` 配下に格納する想定）。
